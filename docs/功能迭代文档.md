2. **单集 PUT 全链路语义验证**（可逆实测）：`PUT type=2` → 单集 type 变 2、条目 `ep_status` 由服务端自动重算 0→1、`updated_at` 刷新；`PUT type=0` 还原后 `ep_status` 回 0——服务端按单集状态重算完成度，与批量 PATCH 行为一致
3. **E2 的基线回读是必要的**：原实现推送成功后以本地时间戳冒充 `serverUpdatedAt`，会导致下一次拉取误判「远端有更新」；回读云端单条收藏后基线准确

5. **修复「移除追番后同步复活」缺陷**：v0 云端无删除收藏端点，移除仅删本地，下次同步拉取会把条目重新建回（表现为「移除没有效果」）。引入**移除墓碑**机制（`animeviewer:removedSubjects` 持久化）：移除时记录 subjectId，拉取合并跳过墓碑条目；显式加追/导入收藏时解除墓碑；移除同时清空该条目的待推单集队列（防止队列重放时 400 兜底把已移除条目重新收藏到云端）。实测：移除 → 成功同步（云端 5 条、本地新增 0）→ 不复活；重新加追 → 推送 1 条回云端
6. **新增「图片镜像地址」可配置项**（设置页 API Base URL 下方）：墙内环境 `lain.bgm.tv` 图片常不可直连，配置后将所有图片 URL 的主机替换为镜像地址（路径保留，支持反代域名或含子路径的前缀），实现于 `PosterImage` 统一出口 + 设置页资料卡头像，配置变更即时生效、留空使用官方源。实测：不可达镜像 → 全部图片按预期降级为占位图；镜像填官方源 → 重写后 URL 结构正确（`镜像 + /r/400 + 原始路径`）且图片正常加载；清空 → 恢复官方源

**前置探测清单（实施首日，沿用 v0.8/v0.14「探测定案后动工」惯例）**：

1. **HLS 直连 CORS 失败的错误形态**：hls.js `Events.ERROR`（networkError 细分：manifestLoadError 等）与直链 mp4 video error 事件的区分——决定 O1「自动经代理重试」的触发条件（仅网络类错误触发，媒体解码错误不重试）；需用户自备一个测试 m3u8 源
2. **m3u8 重写用例固化**：master/media 两级 + EXT-X-KEY（AES-128）/ EXT-X-MAP + 相对/绝对/带查询串分片地址，样例清单直接做 JUnit 固定用例（服务端纯函数，不依赖网络）
3. **代理 Range 透传 curl 基线**：`bytes=0-99` / 后缀区间 / 越界 416，对齐 v0.14 S4 验收口径
4. **WebDAV 样例环境**：rclone serve webdav（或 Docker）起本地服务确认 PROPFIND 响应结构（`DAV:` 命名空间 multistatus、href 百分号编码）——O3 启动前完成
5. **插件共存**：artplayer-plugin-danmuku 与 remux currentTime 拦截、`:key="videoSrc"` 换集重挂载的兼容走查（弹幕池随播放器实例重建，需确认重挂载后弹幕恢复加载与进度对齐）

**风险前置**：

1. **代理滥用面（SSRF / 开放代理）**：白名单空=禁用（默认）+ 仅 http/https + 服务端不存任何源清单（唯一入口为前端手动绑定）三重防线；WebDAV 凭据不进 URL（open → 短时 streamId）；个人局域网服务定位下 DNS rebinding 等残余风险接受并如实记录
2. **体积**：hls.js（gzip ~140KB 级）与 danmuku 插件均独立 chunk、进入播放页才下载——主包体积红线延续（验收记录 chunk 明细对比）
3. **弹幕文件方言**：仅 B 站 XML 文本格式、UTF-8 编码；解析失败整文件拒绝并提示（防静默半导入）；弹幕文件属用户自备内容，同版权边界
4. **清单重写完整性**：漏改一类 URI（如 KEY/MAP）即整流不可播——以探测 2 的用例固化清单覆盖，实测遇未知标签按「原样透传」降级

**决策点（待评审定稿，定稿后动工）**：

1. **O3 WebDAV 是否随本轮实施**：P2 实验项，共享 O2 流式转发地基后增量约 0.5 天；砍掉不影响 O1/O2/O4/O5——建议随轮实施、验收后定去留（与 §7 建议顺序一致）

1. **弹幕插件随播放页常驻挂载**（`danmuku: () => Promise.resolve(props.danmaku ?? [])`）而非「有弹幕才挂载」——ArtPlayer 不支持构造后追加插件，若首次播放无弹幕、中途导入则无法热加载；代价是插件 chunk（gzip 15.4KB）随播放页必下载（与 artplayer 同页，体积红线未破）
2. **代理清单识别双条件**（扩展名 or Content-Type）+ 仅 2xx 改写——防把上游 404 错误页当清单重写后以 200 返回
3. O1 直链容灾只重试一次且不粘性记忆——源可用性随时变化，粘性会让「源恢复直连」永远走代理
4. WebDAV `binding.url` 存未编码的完整文件 URL 仅作标识与进度键（`u:` 前缀），播放一律走 open→streamId 会话流；服务端 joinPath 逐段编码（中文/空格路径——集成测试初版仅 ASCII 未暴露，补 CJK 用例时发现并当场修复）
5. 弹幕存储不进导出备份（XML 可随时重新导入）；`dm:` 记录随 mediaStore 单库存储，与绑定/进度同库

**实现中的设计取舍（已记录）**：
1. **匹配状态机三态**：unmatched（未识别出标题或搜索无结果）/ pending（有候选待确认）/ bound（确认或高置信自动绑定）；解绑回到 pending/unmatched 并保留解析结果

4. 转封装命令仅取首视频轨+首音频轨（`-map 0:a:0?` 可选映射）——多音轨取主轨，v0.15 视需求扩展

**验收中发现并当场修复的三个缺陷（真实价值所在）**：
1. **seek 重拉拿不到用户意图时间**——fMP4 无索引时浏览器把超出 `seekable=[0,0]` 的 seek 静默钳制回 0，`video:seeking` 事件里读到的已是钳制值（首版按 buffered 判断放行原生 seek，实际被吞）。修复：拦截 ArtPlayer 实例的 `currentTime` setter（进度条/热键全部经此，取到原始目标）+ video 元素级兜底监听 + 销毁期守卫
2. **ArtPlayer 事件代理不含 `video:seeking`**——`art.on('video:seeking')` 永不触发（timeupdate/pause 等在代理列表内，seeking 不在），改为直接挂 video 元素
3. **换集播放组件复用不重载**——`#/watch` 同路由不同 query 时 Vue Router 复用组件，`onMounted(load)` 不再执行（表现为旧集继续播放）；补 query 字符串 watch + loadSeq 序号守卫防过期响应竞态

**已知简化（如实记录，见服务 README「已知边界」）**：
1. 转封装流 seek 落点为不晚于目标的关键帧（偏差 ≤ GOP 通常 2~10s，只提前不错过）；进度条在流元数据渐进解析完成前（数秒内）百分比映射有偏差，随后收敛
2. 容器转封装不转编码——H.264/AAC 完全兼容，HEVC 视设备硬解，MPEG4P2/WMV 等浏览器不支持的编码仍不可播
3. 进度条 UI seek 的目标时间以点击时刻播放器已知的 duration 为分母（渐进解析期间偏小），元数据收敛后即准确

**验收后修复（2026-09-13，用户反馈）**：**Bangumi 匹配直连失败**——原实现代理需经启动参数显式传入（`application.yml` 默认 `proxy-host` 为空），用户裸启动 `java -jar` 时走直连被墙重置（`Connection refused`），匹配全挂。修复为**线路自动容灾**：新增 `av.bangumi.proxy-mode`（`auto` 默认 / `direct` / `proxy`），auto 模式下直连失败自动经代理重试一次并粘性记忆可用线路（代理默认 127.0.0.1:7897），墙内 Clash 环境裸启动开箱即用；实测裸启动日志「直连请求失败（Connection refused）→ 切换为经代理重试」后搜索/匹配全部恢复正常。

**验收后优化（2026-09-13，用户评审通过）**：**媒体库管理进度可见化**。原实现文件列表只在扫描结束后刷新一次、匹配阶段状态卡计数停摆，观感为「要等全部匹配完、甚至关闭重开抽屉才刷新」。改动：① 服务端 `ScanStatus` 增加匹配阶段进度字段 `matchTotal/matchDone`，匹配阶段 `currentPath` 实时指向正在匹配的文件名；② 抽屉轮询升级——打开期间持续轮询，扫描运行中每 2s 增量刷新当前列表页（防请求堆积 + 改绑弹窗打开时暂停），完成时 toast「扫描完成：处理 X · 新增 Y · 自动绑定 Z」并刷新列表与目录计数；③ 完成判定采用**扫描代际（startedAt）变化**而非 running 边沿——秒级完成的扫描在两次轮询间开始并结束，边沿判定会整体错过，代际判定对快/慢扫描都可靠；④ **匹配范围收窄（评审采纳）**：仅自动匹配「本轮新增/更新的文件 + 未识别（unmatched）」，待确认（pending）为人工终态不再每次扫描重搜（单文件「匹配」/改绑仍可手动触发）。真实库验证（61 个文件，含用户追加的物语系列/义妹生活等）：全量重扫进度实时推进（「扫描中：已处理 25 … 当前文件名」→「Bangumi 匹配中 x/52」），列表状态标签实时变化，完成 toast 正常弹出，全程未关闭抽屉。

**过程中修复的两个连带缺陷**：① 重写状态机时丢失 `running.set(false)` 且 done 态拷贝保留 running=true——扫描结束后状态永远「运行中」，后续触发全部 409、前端永远看不到完成边沿；② 真实文件暴露解析缺陷：`[JPSC]` 等全大写发布组尾标、`[炫樱字幕组]` 等 CJK 组名被误认成标题——`isNoiseToken` 增补全大写短词（2~10 位）与字幕组/字幕/汉化/搬运关键词，修复后 `[Nekomoe kissaten][Monogatari Series…][14][1080p][JPSC].mp4` 正确解析出标题与集数。

### 边界（产品定位的有意扩展，原样入档）

v0.15 前「不提供资源检索」的版权边界自本路线起**有意扩展**为「RSS 站点适配器」：应用本身不托管、不缓存、不转存任何资源内容，仅提供磁力链接的解析、提交至用户自备的 BT 引擎、与用户自有文件的播放管理；站点内容由站点方提供，服务端仅抓取公开 RSS 接口、**不绕过任何反爬防护**；下载行为的合规性由使用者自担、仅限个人使用。

### 风险前置

1. **冷门磁力无种/慢**：DHT bootstrap 需要时间——acgnx 磁力自带 opentracker + tracker 注入列表可配（ngosang/trackerslist 格式）+ 界面如实显示 peer 数，不伪装「下载中」
2. **aria2 为外部依赖**：沿用 ffmpeg 模式——路径可配、健康探测、异常重启；未配置全链路降级（添加磁力 → 一键复制 + 指引）
3. **`rss.xml` 参数面未逐项验证**（order/分类/字幕组/分页形态）——列入实施首日前置探测 1
4. **下载目录中文/空格路径**：aria2 `dir` 参数 + S2 扫描器兼容回归（v0.14 joinPath 逐段编码教训直接复用）
5. **非目标（顺延）**：边下边播（BT 顺序下载流式播放——aria2 顺序下载支持弱，登记调研不排期）；.torrent 文件本体托管；下载行为的对外可见性由用户 BT 客户端行为决定，应用不做匿名化

### 优化定案：评分判定后置（2026-09-15 用户实测定案，v0.20 交付当日修订）

- **问题**：首版评分/阈值判定发生在检索落库当轮（前置阶段）——而 infohash 跨轮去重使已落库命中**永不重评**：先以阈值 0 订阅产生 pending、再调高阈值时因 0 新命中，存量 pending 不会自动入队（体感「使用评分机制后订阅大概率匹配不到任何数据」）。
- **定案（按用户需求）**：评分机制**不用于前置搜索阶段**——doCheck 落库循环去掉评分驱动的 auto 分支，通过基础过滤（集数/去重/大小/屏蔽字幕组）的资源**全部先落待确认队列**（评分仍计算落库供展示与转队判定）；评分仅用于「待确认 → 自动加入队列」：`autoEnqueuePending` 扫描本订阅 pending，score≥阈值经三重保护后 enqueue 转 auto（note「匹配度 N≥阈值 M，自动入队」，409 转 enqueued），单轮 MAX_HITS_PER_CYCLE 上限；调度 tick 对阈值>0 的订阅**每轮（≤30s）执行转队**，不依赖 RSS 检索到期——阈值/偏好调整后存量 pending 最迟 30s 内重新评估。
- **语义收益**：搜索阶段零评分过滤（命中 100% 落库可见）+ 存量 pending 可重评 + 阈值调整即时生效；三重保护（日限/单限/仅已匹配）与单轮转队上限照常兜底。
- **实测**：阈值 0 检索 10 条全 pending（100/85/60 落库不转队）→ 改阈值 60 **不触发检索** → tick 扫描 5 条达标转 auto + 第 6 条起日限降级——全通（提交 db66532，mvn test 75 用例全绿）。
- **附带环境定案**：服务进程被强杀时托管 aria2 残留（Windows 允许双实例同绑 16800）致 RPC Unauthorized、自动入队失败——清理残留 aria2 + 「重启引擎」恢复；下次遇到 Unauthorized 先查残留 aria2 进程。

## 5I. v0.21 补记：订阅集数解析尾数劫持修复（2026-09-16 当日修复）

### 排查记录（2026-09-16 实测复现）

- **传参链路**：订阅检索关键词=条目中文名/原名双查询（`SubscriptionService.searchMerged`），逐词调 `resources.search(kw, null)`（不指定站点=全部站点混合），按站点 `searchTemplate` 拼 RSS URL（acgnx `rss.xml?keyword=`、dmhy `topics/rss/rss.xml?keyword=`，百分号编码）。
- **中文名关键词是死权重**（实测）：简体中文全句在两站 RSS keyword（标题子串匹配）下均 **0 条**——LoliHouse 发布标题用简体转述「转校生美少女竟是我曾经认为是男孩子的青梅竹马」+ 繁体「轉學後班上的清純可愛美少女…哥兒們」，与 Bangumi 简体名不构成子串（繁简转换 + 字幕组转述差异）。
- **原名关键词**拉回 ~29 条：LoliHouse 第 01~11 话 ×2 站、JMAX OP/ED 单曲 ×2、raw 第01-04巻、雲雀湯 1-3 epub。
- **根因 1（主）**：`SubscriptionFilter.parseEpisode` 独立数字退化取「最后一个非年份非 1080p 独立数字」——LoliHouse 标题**无「第N话」**、集数是裸数字（`てんびん - 11`），而尾部 `HEVC-10bit` 的 10 排最后 → **第 01~11 话全部解析成 10**（原测试以「已知启发式行为，不修正口径」钉死此行为）；`existsPendingEpisode` 同集 pending 占位唯一 → 第一条落库后其余 10 条全被挡。JMAX 同理被 `FLAC 96kHz/24bit` 的 24 劫持（OP 被 pending(24) 挡掉）；raw `第01-04巻`→4、novel `1-3`→3 为范围包误判单集。
- **根因 2（旁证）**：19:33 首检日志「阈值第 10 话」来自当时 download_tasks 里有该条目第 10 话任务（阈值=max(基线, 下载最大集, 媒体库最大集)），任务随后被人工清理——非本次缺陷。

### 修复定案（两端同步，保持「两端口径一致」硬要求）

- **服务端** `SubscriptionFilter.parseEpisode` 独立数字退化新增三类排除：①**单位尾数**（大小写不敏感 bit/kHz/Hz/kbps/mbps/fps——24bit、48kHz、192kbps、60fps）；②**点分邻接**（数字两侧贴 `.`：2026.07.08 日期段、H.264/H.265 编码名、Vol.12 卷号、3.4GB 大小）；③**连字符范围成员**（数字-`-`-数字直接相连：第01-04巻、1-3 epub 区间包无单集语义，整段作废）。
- **前端** `mediaService.guessEpisodeSortFromTitle` 同步同规则；影响面=确认弹窗预填——范围包/单曲的预填从垃圾数字变为 null（用户手填），与订阅命中仍同口径。
- 修复后口径：LoliHouse `てんびん - 01~11` 逐话正确解析（11 条全可命中）；JMAX OP/ED、raw 卷、novel epub → null（无集数不入队列，语义正确——本就不该命中）。
- **存量数据不迁移**：现有 4 条错误 pending（#195-198）受 infohash 跨轮去重保护不重评；人工忽略/清空历史后重新检索即按新口径重建（#195 实为第 11 话，重检会以正确集数重新命中，下载时 409 去重兜底不会重复下载）。

### A.3 硬约束与风险

1. **v0 无「删除收藏」端点**：`/v0/users/-/collections/{subject_id}` 仅支持 POST（upsert）与 PATCH（进度），规范中全部 DELETE 方法均在 indices / collect 相关路径上。因此**条目**的取消收藏/抛弃状态无法推送云端（与 v0.3「4=搁置 5=抛弃 不同步」的处理一致）；**角色**收藏的取消端点（`DELETE /v0/characters/{id}/collect`）规范已声明但服务端实测未实现（404 路由未注册），取消收藏当前只能通过 bgm.tv 网页端操作；**人物**收藏的取消端点（`DELETE /v0/persons/{id}/collect`）2026-09-07 探测同样 404（与角色同构），v0.7 F2 沿用「仅本地移除」处理。
2. **搜索接口仍为实验性 API**：D3/D4 依赖的 filter 字段 Schema 可能变动——延续「API 层单文件收口」对策。**v0.5 实测结论**：`meta_tags` 服务端过滤不可用（与 tag 一同恒 0），D4 按预案保留客户端排除；另发现 `air_date` 不支持 `<=`（已绕开）。
3. **单集 PUT 与批量 PATCH 并存**：E1 上线后两条写路径并存，需在同步队列中统一（单集标记同样入 dirty 队列重放）。
4. **2026-09-07 线上探测记录**（无鉴权请求区分路由注册状态：已注册→401 / 未注册→404）：`GET /v0/users/-/collections/{subject_id}/episodes` 401（可规划，F1）；`GET /v0/users/{username}/collections/-/persons` 200（公开可用，F2）；`POST /v0/indices/{id}/collect` 401（已注册但无读端点，F5 建议不采纳）；`DELETE /v0/persons\|characters/{id}/collect` 404（均未实现）。另：`GET /v0/subjects` 参数盘点无 `airing` 过滤（type/cat/series/platform/sort/year/month），legacy `/calendar` 迁移路径（技术选型文档 §6）暂不可行。
5. **吐槽（评论）读写官方 v0 API 均无端点**（2026-09-08 复核 `v0.yaml` 全部 8 个端点分组 + bangumi/server#526 feature request 仍 open）：仅 `GET /v0/episodes/{episode_id}` 响应的 `comment` 字段提供吐槽数量（只读 int）。bgm.tv 网页吐槽区无法客户端绕行（主站无 CORS 头、`X-Frame-Options` 禁 iframe、next.bgm.tv p1 未文档化），G3 以「吐槽数 + 官网外链」为终态，待官方评论 API 落地后升级内嵌评论区。
