## 1. 背景与约束

AnimeViewer 是一个本地优先的动漫追番面板，第一期目标是最小可用产品（MVP）：每周新番时间表、条目详情、搜索筛选、本地追番管理。选型时明确以下约束：

- **第一期无自建后端**：纯前端 SPA，直接调用第三方开放 API，降低部署与维护成本；v0.14 起为播放场景引入**可选**的自建本地后端（Java，见 §3.7）——本地优先原则不变，不部署服务时应用仍为纯前端形态
- **数据源在国内部分网络环境不可直连**（实测 `api.bgm.tv` 直连超时，走代理正常），必须支持 API 地址、Token 可配置
- **迭代速度优先**：第一期为功能验证期，避免引入过重的工程化设施
- **未来可能桌面化**：技术栈需能平滑迁移到 Tauri

## 3. 关键选型理由

### 3.1 Vue 3 + TypeScript + Vite

- 面板类应用以「列表 + 卡片 + 表单」为主，Vue 单文件组件的表达效率高
- Vite 冷启动 < 2s，HMR 即时生效，契合快速迭代节奏（第一期开发中已验证）
- strict 模式全量类型检查（`vue-tsc -b`），第一期即捕获了 5 类模板类型错误

### 3.2 Naive UI（对比 Element Plus / Arco）

| 维度 | Naive UI | Element Plus | Arco Design |
|------|----------|--------------|-------------|
| 暗色主题 | 一等公民，`darkTheme` 一行切换 | 需手动配 CSS 变量 | 支持 |
| TypeScript | 全量 TS 编写，类型最完整 | 良好 | 良好 |
| 主题定制 | `themeOverrides` 对象式，无需 SCSS | SCSS 变量 | less 变量 |
| 体积 | 按需 tree-shaking 良好 | 较大 | 中等 |

动漫类应用默认暗色审美，Naive UI 的暗色支持与零配置定制是决定性优势。已用 `themeOverrides` 将主色定为紫色系（`#8a7bff`）。

**踩坑记录（v0.30 补记二，2026-09-25 实测定位）**：

1. `NSwitch` 的 `#checked/#unchecked` 槽位文字依赖隐藏 placeholder 撑开自身宽度，但 `.n-switch` 与 rail 的 `min-width` 是**主题定值**（`--n-width`/`--n-rail-width`）且 rail `overflow:hidden`——开关作为 flex item 被收缩时，文字宽度不参与 min-content 保护，「开/关」会被静默裁切。防御写法：开关所在行容器内对其设 `flex-shrink: 0`。
2. `NFormItem` 默认插槽内容区为 **flex 横排**——同一 FormItem 下多个 `width:100%` 的块会被挤成并排多列（不是直觉上的纵向堆叠），多控件块内再叠固定宽度控件即过约束折行。多开关行统一用显式纵排容器（`flex-direction: column`）承接近百宽度子块，每块独占一行。
3. `NCollapse` 折叠头内部间距**不能靠 `:deep` 写 padding 直接覆盖**（v0.30 补记三，2026-09-25 实测定位）：样式源码（cssr）中 `&:first-child > header { padding-top: 0 }` 编译后优先级 (0,4,0)、`header { padding: var(--n-title-padding) }` 为 (0,3,0)——`.x[data-v] .n-collapse-item__header`（(0,3,0)）与其平局时运行时后注入者获胜，且首项 `padding-top` 恒被强制清零（实测收起态标题距顶仅 2.8px、距底 12.8px）。防御写法：**垂直留白写在自有内容元素上**（组件不会为自定义类生成规则，无优先级之争），`:deep` 只做清零复位，且选择器需带 `.n-collapse-item:first-child` 前缀（(0,5,0)）压过其 `&:first-child` 链。

### 3.3 Bangumi API（数据源）

- 免费开放、无需申请即可读取，条目/封面/评分/放送数据齐全，中文元数据质量最高
- CORS 开放，浏览器可直连，无需服务端代理
- 使用的接口：

| 接口 | 用途 | 状态 |
|------|------|------|
| `GET /calendar` | 每周放送表（按星期分组） | 稳定（legacy 接口） |
| `GET /v0/subjects/{id}` | 条目详情（含 infobox/tags） | 稳定 |
| `POST /v0/search/subjects` | 搜索 + 过滤（`filter.tag`、`nsfw`）+ 排序 | 实验性，Schema 可能变动 |

**已验证的关键细节**（踩坑记录）：

1. 搜索过滤字段是 `filter.tag`（单数）而非 `tags`，多值为「且」关系，支持 `-前缀` 排除
2. legacy `/calendar` 不返回 `nsfw` 字段，无法在周历侧过滤 R18（v0 详情接口才有）
3. 浏览器安全策略禁止自定义 `User-Agent` 头；Bangumi 对匿名请求有速率限制，配 Access Token（`Authorization: Bearer`）可提升
4. 匿名搜索默认即排除 R18（官方行为），详情接口需注意 `nsfw` 字段

### 3.4 Pinia

- 官方推荐，Options API 写法与 Vue DevTools 集成好
- **踩坑记录**：动态键 `Record<string, T>` 不能直接作为 state 根对象——getter 收到的第一个参数实际是 store 实例（混入 actions/内部方法，`Object.keys` 结果被污染）。已改为具名键包裹（`{ items: Record<...> }`）。此约束已写入 store 代码注释

### 3.5 Hash 路由

选择 `createWebHashHistory` 而非 History 模式：未来打包为 Tauri/静态文件直接打开时无需服务端 rewrite 配置，部署零依赖。

### 3.6 播放器：ArtPlayer + hls.js（v0.13 规划）

播放为三种形态（本地直连 / 服务端媒体库流 / 在线自备源）的公共能力，播放器一次选型、全形态复用。

| 维度 | ArtPlayer | xgplayer（西瓜） | video.js | 原生 video |
|------|-----------|------------------|----------|------------|
| 体积 | 小 | 中 | 大（插件生态重） | 0 |
| 文档/社区 | 中文文档完善，国内媒体类项目广泛使用 | 中文文档，字节系 | 英文为主 | — |
| 弹幕插件 | artplayer-plugin-danmuku 成熟 | 有（需配套） | 需第三方 | 无 |
| 自定义 UI / API | 控制栏与事件 API 丰富，样式可完全接管 | 较好 | 皮肤机制较重 | 全部自研 |

**结论**：ArtPlayer（MIT）为主播放器——弹幕需求（v0.15）可直接复用官方弹幕插件，体积最小；HLS 场景叠加 hls.js（基于 MSE，仅 m3u8 源时动态 import；Safari 原生 HLS 也统一走 hls.js 保证行为一致）；原生 `<video>` 保留为最简兜底路径。**硬约束**：延续 v0.10 主包体积红线——播放器相关 chunk 全部动态 import 独立打包，不进业务主包，未进入播放页零下载；最终体积以 v0.13 落地实测回填本节。

**落地实测回填（v0.15，2026-09-13 交付）**：实际版本 artplayer 5.4.0 + artplayer-plugin-danmuku 5.3.0 + hls.js 1.7.3。chunk 实测：artplayer 142KB（gzip 37.5）+ danmuku 插件 55KB（gzip 15.4）+ hls.js 595KB（gzip 185.8，高于规划预估 ~140KB，如实记录）——三者独立 chunk 仅播放页下载，业务主包 49.05KB（gzip 15.17，较 v0.14 +0.2KB）红线未破。实施取舍：danmuku 插件随播放页常驻挂载（ArtPlayer 不支持构造后追加插件，中途导入弹幕需热加载 `danmuku.load()`）；hls.js 经 ArtPlayer `customType` 接入，MSE 索引下原生 seek（与转封装流的 seek 重拉路径互不干扰）。详见迭代文档 §5A v0.15 实现记录。

### 3.7 后端服务：AnimeViewerService（Java 21 + Spring Boot，v0.14 规划）

**定位与边界**：局域网个人媒体服务（工程落位 `G:\iflow\app\AnimeViewerService`，独立 Java 工程）。解决三件事：① mkv 等容器浏览器不可播 → ffmpeg 转封装 fMP4 流；② 手机/平板等局域网设备播放；③ 文件名 → Bangumi 条目/集数自动匹配（服务端调用可自定义合规 User-Agent，顺带解决 §3.3-3 浏览器 UA 限制）。**可选组件**：不部署服务时应用保持纯前端形态（v0.13 本地直连不受影响）。**版权边界**：仅索引与播放用户自有文件、代理用户手动添加的源，不内置任何在线播放源、不提供资源检索。

| 项 | 选型 | 理由 / 备选说明 |
|----|------|-----------------|
| 语言/运行时 | Java 21（LTS 基线） | 用户指定 Java 技术栈；LTS 长期支持；可开启虚拟线程利好流式 IO |
| 框架 | Spring Boot 3.5.x | 生态成熟，MVC `ResourceRegion` 原生支持 HTTP Range 流式响应；对比：Node 流式友好但非指定栈；Go 单二进制优秀但需自研面更大 |
| Web 层 | spring-boot-starter-web（同步 MVC） | Range 文件流与转封装 pipe 流均为阻塞模型友好场景；不引 WebFlux（复杂度与收益不成比例） |
| 索引库 | SQLite（sqlite-jdbc）+ Spring JdbcClient | 单文件零运维（media.db）；万级文件索引远不需要独立数据库服务；不引 ORM |
| Bangumi 客户端 | RestClient | 服务端直连无 CORS 问题，可自定义合规 User-Agent |
| 转封装/探测 | ffmpeg / ffprobe 外部进程（ProcessBuilder） | mkv→fMP4 用 `-c copy` 不重编码，CPU 占用极低；不引 JavaCPP ffmpeg-platform（平台原生库体积过大，违背轻量原则）；用户自备 ffmpeg，路径可配，未配置时 mp4 直连流仍可用（功能降级） |
| 鉴权 | 启动生成随机 Token（控制台输出 + 本地文件）+ `X-AV-Token` 请求头 | 首次配对制；默认仅绑定 127.0.0.1，开启局域网监听需显式配置确认 |
| 构建/交付 | Maven 单模块 → 单可执行 jar（`java -jar`） | 与前端解耦部署；前端设置页配置「服务地址 + Token」 |

**关键技术点（v0.14 S4，风险最大）**：转封装流为「直播式」流，不支持随机跳转——seek 采用**重拉**策略：播放器 seek 事件 → 携带 time 参数重新请求 → 服务端 `ffmpeg -ss <t>` 重启转封装。需在实施首日原型验证（迭代文档 §7 v0.14 建议顺序已置顶）。

**落地实测回填（v0.14，2026-09-12 交付）**：实际版本 Java 21.0.11（Microsoft OpenJDK）+ Spring Boot 3.5.6 + sqlite-jdbc 3.41.2.2 + ffmpeg 2026-05-28 gyan full build。原型验证补充两个关键实测结论：① fMP4（empty_moov 无索引）在浏览器中 `seekable=[0,0]`，超出缓冲的 seek 被浏览器静默钳制——seek 重拉必须在播放器层拦截 seek 调用取用户意图时间（ArtPlayer 实例 currentTime setter），不能依赖 seeking 事后事件；② api.bgm.tv 服务端直连在墙内被重置，服务已内置可选 HTTP 代理配置。详见迭代文档 §5C。

### 3.8 BT 下载引擎：aria2 外部进程（v0.16 规划）

**定位**：v0.16~v0.18 磁力下载路线（迭代文档 §5D）的下载执行层——应用不实现 BitTorrent 协议，由 aria2 承担（DHT/PEX/加密/select-file 全部现成），服务端仅经 JSON-RPC 管理任务。

| 维度 | aria2（外部进程）✅ | qBittorrent（WebUI 对接） | jlibtorrent（JNI 内嵌） |
|------|---------------------|---------------------------|--------------------------|
| 部署 | 单 exe 约 5MB，服务端 ProcessBuilder 自动拉起，也可对接已有实例 | 需用户安装完整客户端并开启 WebUI | 零外部依赖，但 native 库 30MB+/平台 |
| 协议能力 | magnet/DHT/PEX/加密/select-file 齐备 | 齐备（libtorrent 内核） | 齐备（libtorrent 内核） |
| 集成方式 | JSON-RPC（HTTP），addUri/tellStatus/changeOption 等数个方法即够 | REST API，功能面大但强绑定其任务模型 | Java API，JNI 升级维护成本高 |
| 降级策略 | 未配置时「一键复制磁力」手动兜底（沿用 ffmpeg 外部依赖模式） | 未装客户端即不可用 | 无降级问题但重依赖 |

**结论**：aria2 外部进程——与 ffmpeg 同一外部依赖模式（路径可配、健康探测、异常重启、未配置功能降级），零 jar 依赖、体积红线不破坏；服务端建下载引擎抽象层，qBittorrent WebUI 适配器登记为后续可选扩展（不排期）。风险前置：addUri 暂停态 → 元数据回读 → select-file → unpause 链路实施首日原型验证（迭代文档 §5D 前置探测清单 2）。

**落地实测回填（v0.16，2026-09-13 交付）**：实际版本 aria2 1.37.0 Windows build。原型验证修正了规划中的三个假设：① 磁力**不能**以暂停态入队（暂停态永不解析元数据）——active 入队 + 多文件选择在元数据解析后经「暂停→changeOption(select-file)→恢复」应用（暂停态 changeOption 写入实测可行）；② **磁力元数据完成后负载是新 gid**（原 gid 标记 complete）——watcher 按 tellStatus 的 infoHash 收养后继 gid；③ Windows 版 schannel 吊销检查致 HTTPS tracker 握手失败——托管拉起默认 `--check-certificate=false`；④ `.torrent` 直链 addUri 存在「种子 gid + 负载新 gid」二段行为——服务端抓种子内容直接 addTorrent（文件清单立即可知）。运行配置存服务端 SQLite settings 表（yml 默认值），与代理白名单的 yml-only 决议差异化（下载配置无 SSRF 面）。详见迭代文档 §5D。

### 3.9 桌面壳与分发打包：Tauri 2 + 内置媒体服务 sidecar（v1.0，2026-09-26 评审通过）

**定位**：可分发的 Windows 桌面应用（NSIS 安装包 + 绿色 exe 双形态）——壳复用全部 Web 代码，内置媒体服务消除「装 JDK 21 / 配 ffmpeg / 配 aria2」三条使用门槛。规划依据：迭代文档 §5 v1.0 节（D1~D4 拆解）；部署形态见部署指南 §4A。

**壳选型维持 Tauri 2**（2026-09-12 既定 + 2026-09-26 复核定案）：

| 维度 | Tauri 2 ✅ | Electron | Wails |
|------|-----------|----------|-------|
| 体积 | 壳级 ~5MB（WebView2 系统组件复用） | 每应用捆绑 Chromium+Node，80MB+ | 小（Go + WebView） |
| 官方插件 | http/notification/single-instance/window-state 齐备 | 最成熟 | 较少 |
| 后端语言 | Rust（改动面收敛在壳胶水层 main.rs） | Node/JS | Go |
| 决定性因素 | 老分支 `feat/v1.0-s1-desktop` 已全链路验证（NSIS+绿色 exe/单实例/窗口状态/UA/通知/E2E），按文件移植成本最低 | 打包体积与内存对本应用无补偿收益 | 生态小、无既有验证 |

**架构（自动桥接）**：前后端松耦合不变（服务地址/Token 运行时配置，无构建期绑定）——桌面版只是把「用户手配」自动化：

```
Tauri 壳启动
  ├─ 拉起内置服务端 sidecar（注入 --av.data-dir=%APPDATA%/AnimeViewer/data
  │    与包内 ffmpeg/aria2 路径；8787/16800 端口与 Web 形态一致）
  ├─ 轮询 GET /api/health 就绪 → 读 data/token → 回填前端 svcUrl/svcToken
  │    （用户已在设置页手动配置则以手动为准，不覆盖）
  ├─ 服务端 --av.parent-pid 心跳：ProcessHandle.of(pid).isAlive() 探测壳进程
  │    死亡即自杀（防孤儿进程占用端口）——服务端本期唯一代码改动
  └─ 退出：壳 kill sidecar → 服务端 @PreDestroy 收尾 aria2 子进程（既有链路）
```

**分发打包矩阵（2026-09-26 评审定案）**：

| 组件 | 打包？ | 体积（估） | 口径 |
|---|---|---|---|
| 前端 dist | ✅ | ~3MB | Tauri `frontendDist`，Hash 路由零 rewrite（§3.5 既定收益） |
| 服务端 fat jar | ✅ | ~25MB | 桌面版核心价值：媒体库/下载/订阅开箱即用 |
| JRE | ✅ jlink 裁剪 | 45~60MB | jdeps 算模块集裁剪，消除 JDK 21 安装门槛 |
| aria2c | ✅ | ~5MB | 服务端托管模式既有（§3.8），注入包内路径零代码改动 |
| ffmpeg / ffprobe | ✅ 默认带可裁 | 解压 ~150MB | essentials GPL 构建；NSIS 可选组件默认勾选；**否决「首启引导下载」**（离线不可用 + 校验复杂度不值） |
| qBittorrent | ❌ | — | 独立 GUI 应用；维持 v0.18「检测到已安装则直开」用户定案（2026-09-26 评审重申，永不随包分发） |
| WebView2 | 系统组件 | — | Win10/11 自带；NSIS downloadBootstrapper 兜底 |

安装包体积估算：原始 ~240MB → NSIS LZMA 压缩后 ~90~120MB（以 D3 实测回填本节）。

**许可合规**：ffmpeg essentials 构建含 libx264（GPLv3）、aria2 GPLv2——均为独立进程经 RPC/管道调用，不构成链接衍生（mere aggregation），应用本身许可不受传染；合规动作 = 关于页标注第三方许可 + 提供源码获取途径。

**落地实测回填（v1.0 D2，2026-09-26 交付）**：jlink 裁剪 JRE 实测 **51MB**（17 模块：jdeps 静态输出 ∪ 反射型基线 java.base/java.sql/java.xml/java.naming/jdk.crypto.ec，预估 45~60MB 命中）；NSIS 安装包实测 **80.1MB**（壳 13.9MB + JRE/JAR 增量，低于规划估算 90~120MB）。**关键踩坑**：Tauri 2 `resource_dir()` 返回 `\\?\` 扩展前缀路径——CreateProcess 可拉起 `\\?\G:\...java.exe`，但 JVM 打不开 `-jar \\?\G:\...` 形式的 jar（恒报 Boot loader ClassNotFoundException，且 bash 手动跑同参数成功极易误判）；壳侧须 `strip_prefix(r"\\?\")` 后再拼 java/jar 参数。数据落 `%APPDATA%/AnimeViewer/data`，服务日志 `%APPDATA%/AnimeViewer/logs/{service,shell}.log`。端到端冒烟：启动 → t+8s 健康就绪 → 强杀壳 → ~9s 服务端 parent-pid 心跳自杀退出。详见迭代文档 §5 v1.0 D2 实现记录。

**落地实测回填（v1.0 D3，2026-09-26 交付）**：随包二进制实测——aria2 1.37.0（5.4MB）+ ffmpeg/ffprobe gyan **full build**（各 ~215MB，合计 435MB，评审估算 ~150MB 基于 essentials 误估）；**NSIS LZMA 压缩率 ~65%**：完整版安装包 **199MB**（D2 纯 JRE 版 80.1MB）、精简版 80.1MB。定案偏差说明：「NSIS 组件化」以**双发布物**实现（完整版/`-lite` 精简版）——Tauri 2 NSIS 模板不支持自定义组件选择页。GPL 合规落地：许可文本随包 `service/licenses/`，设置页「关于与开源许可」块标注（独立进程调用不构成单一程序）。壳路径注入实证：`--av.ffmpeg-path/--av.ffprobe-path/--av.aria2.path` 指向 `service\bin\`（shell.log 记录），精简版正确跳过走 PATH 降级。详见迭代文档 §5 v1.0 D3 实现记录。

**风险与验证点**：① FSA 文件句柄持久化在 WebView2 需 D1 实测（v0.13 规划已预判 Chromium 内核兼容）；② 无签名 exe 有 SmartScreen 提示，签名证书挂账；③ 8787 被占时壳提示启动失败，Web 功能不受影响；④ T3 Token 自动刷新（keyring）不在本期（迭代文档 §5 v1.0 T 表挂账）。

## 4. 数据流架构

```
视图层 (views/)
   │  调用
   ▼
数据门面 dataSource ──┬── 在线模式 → bangumiApi (fetch, 可配 baseURL/Token)
   │                  └── 演示模式 → demo (内置离线数据)
   ▼
状态层 (Pinia: settings / library) ── 持久化 ──► localStorage / IndexedDB（v0.10 缓存持久层）

播放层 VideoPlayer（ArtPlayer，v0.13 起）
   ├── 本地直连：File System Access API / 拖拽（Chromium，v0.13）
   ├── 媒体服务：AnimeViewerService Range 流 / ffmpeg 转封装流（v0.14）
   └── 在线自备源：直链 / hls.js / 服务代理（v0.15）

下载层（v0.16 起，可选）aria2 外部进程（JSON-RPC，服务端管理，§3.8）
   └── 磁力/种子 → 下载目录 ──► 复用媒体库扫描/匹配入库（v0.14 S2/S3）──► 播放层
```

- `dataSource` 门面统一隔离「在线/演示」两种模式，视图层无感知
- `settings`（主题/数据源/BaseURL/Token）与 `library`（追番条目）均 localStorage 持久化，key：`animeviewer:*`
- 播放层（v0.13 起）独立于数据门面：播放绑定 `mediaBindings` 与进度 `watchPositions` 入 IndexedDB；媒体服务为可选组件，未配置时播放层退化为本地直连（v0.13）与自备源直链（v0.15）
- 下载层（v0.16 起）：aria2 经 JSON-RPC 由服务端管理（§3.8）；完成文件落下载目录后复用媒体库扫描/匹配/播放链路（迭代文档 §5D），未配置引擎时前端降级为「一键复制磁力链接」

## 6. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| `api.bgm.tv` 不可直连 | 核心功能不可用 | 已内置：Base URL 可指向自建反代 + 演示数据模式兜底；文档引导配代理 |
| v0 search 实验性 Schema 变动 | 搜索/筛选失效 | API 客户端集中收口（单文件），字段变更只改一处；已按官方 yml 规范对齐 |
| 旧 `/calendar` 接口未来下线 | 周历失效 | 迁移路径：`GET /v0/subjects?airing=true`（待官方完善）或聚合搜索 `air_date` 近期过滤 |
| localStorage 容量/被清 | 收藏丢失 | v0.2 导出/导入 JSON；v0.3 云同步后彻底解决 |
| 匿名请求速率限制 | 批量请求被限 | 引导配置 Access Token；条目详情做内存缓存（日历已做 5min TTL） |
| mkv/avi 等容器浏览器不可播 | 本地播放格式受限 | v0.13 如实标注能力边界（mp4/webm 可播）；v0.14 服务端 ffmpeg 转封装 fMP4 解决 |
| ffmpeg 为外部依赖 | 服务端转封装/探测不可用 | 服务端就绪探测 + 安装引导；未配置 ffmpeg 时 mp4 直连流播放仍可用（功能降级） |
| 局域网服务暴露 | 媒体文件被未授权访问 | 默认仅绑定 127.0.0.1 + 随机 Token 配对 + 开启局域网监听需显式确认 |
| 在线播放版权风险 | 应用被用于盗版内容 | 产品原则（v0.15）：不内置任何播放源、仅支持用户自备源；v0.16 起边界**有意扩展**为 RSS 站点适配器——不托管/不缓存/不转存内容、仅公开 RSS 接口、不绕反爬，合规自担（迭代文档 §5D 边界节） |
| 磁力冷门资源无种/下载慢 | 下载任务停滞 | acgnx 磁力自带 opentracker + 公共 tracker 列表注入可配 + 界面如实显示 peer 数 |
| 站点 RSS 未来加反爬 | 资源搜索失效 | 边界不绕盾；降级为手动粘贴磁力（RSS-only 决议，迭代文档 §5D R4） |
| 无签名安装包被 SmartScreen 拦截 | 桌面版分发体验受损 | v1.0 如实提示「更多信息→仍要运行」；代码签名证书挂账（成本项，视分发范围再购，迭代文档 §5 v1.0 D4） |
| 桌面版 8787 端口被占 | 内置服务启动失败 | 壳健康检查超时后显式提示；Web 功能不受影响，可切「外接」模式自配端口（§3.9） |
